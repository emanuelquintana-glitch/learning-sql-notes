** Capítulo 1 — A Little Background
*** Resumen

SQL es un lenguaje diseñado para interactuar con bases de datos relacionales.
El modelo relacional (Codd, 1970) organiza los datos en tablas (relaciones)
con filas (tuplas) y columnas (atributos). SQL tiene tres sublengajes:

- *DDL* (Data Definition Language): CREATE, ALTER, DROP
- *DML* (Data Manipulation Language): SELECT, INSERT, UPDATE, DELETE
- *DCL* (Data Control Language): GRANT, REVOKE

*** Conceptos clave

- *Entidad*: objeto del mundo real representado en la BD (cliente, cuenta)
- *Clave primaria*: columna(s) que identifican únicamente cada fila
- *Clave foránea*: columna que referencia la PK de otra tabla
- *Normalización*: proceso de eliminar redundancia en las tablas
- *Conjunto de resultados*: tabla no persistente devuelta por un SELECT

**  Sistemas de bases de datos no relacionales

Esta seccion contiene alguna informacion de fondo sobre sistemas de bases de datos pre-relacionales. Durante las primeras varias decadas de sistemas de bases de datos computarizados, los datos se almacenaban y se representaban a los usuarios de diversas maneras. En un sistema de base de datos jerarquico, por ejemplo, los datos se presentaban como una o mas estructuras de arbol.

Tanto los sistemas de bases de datos jerárquicos como los sistemas de bases de datos en red están vivos y saludables hoy en día, aunque generalmente en el mundo de los mainframes. Además, los sistemas de bases de datos jerárquicos han disfrutado de un renacimiento en el ambito de los servicios de directorio, como el Active Directory de Microsoft y el servidor de directorio de codigo abierto Apache. Sin embargo, a partir de la decada de 1970, surgio una nueva forma de representar datos, que era mas rigurosa pero facil de entender e implementar.

** El Modelo Relacional

En 1970, el Dr. E. F. Codd del laboratorio de investigacion de IBM publico un articulo titulado "A relational Model of Data for Large Share Data Banks" que propuso que los datos se representaran como conjuntos de tablas. En lugar de utilizar punteros para navegar entre entidades relacionadas, se utilizan datos redundantes para vincular registros en diferentes tablas.

# Notas de Estudio: Un Modelo Relacional de Datos para Grandes Bancos de Datos Compartidos (E.F. Codd, 1970)

## 1. Desglose Conceptual Profundo

**Conceptos Centrales:**

*   **Independencia de Datos (Data Independence):** Es la premisa fundamental. Se define como la capacidad de los programas de aplicación y las actividades de los terminales para permanecer inalterados frente a cambios en la representación interna de los datos (física) e incluso en ciertos aspectos de la representación externa (lógica).
    *   *Intuición:* La separación estricta entre "qué datos existen" y "cómo se almacenan". El usuario interactúa con una abstracción lógica, no con direcciones de memoria o estructuras de punteros.
*   **Modelo Relacional vs. Modelo de Red/Árbol:** Codd argumenta que los modelos existentes (jerárquicos o de red) imponen una estructura artificial de acceso (punteros, caminos de acceso) que viola la independencia. El modelo relacional, basado en la teoría de conjuntos y relaciones $n$-arias, describe los datos solo con su "estructura natural".
*   **Relación $n$-aria:** Una tabla plana donde cada fila es una tupla y cada columna es un atributo. No hay anidamiento ni punteros explícitos entre registros.
*   **Orden, Indexación y Caminos de Acceso Dependientes:**
    *   *Dependencia de Orden:* La suposición de que los datos se presentan en un orden físico específico (ej. ordenado por ID).
    *   *Dependencia de Indexación:* La necesidad de conocer índices específicos para recuperar datos eficientemente.
    *   *Dependencia de Camino de Acceso:* La necesidad de navegar explícitamente a través de una red de punteros (como en el modelo CODASYL) para encontrar datos relacionados.

**Supuestos (Axiomas) Fundamentales:**

1.  **El usuario no debe conocer la implementación física:** Cualquier servicio que exponga detalles de almacenamiento es insuficiente.
2.  **La estructura natural de los datos es plana:** Las relaciones de datos pueden representarse adecuadamente sin superponer estructuras de control de flujo o navegación.
3.  **La teoría de relaciones es suficiente:** La lógica de primer orden y la teoría de conjuntos proveen el marco matemático necesario para modelar consultas y actualizaciones sin recurrir a procedimientos imperativos de acceso.

## 2. Formalización Algebraica y Matemática

Aunque el texto proporcionado es introductorio y define el problema, el modelo se formaliza matemáticamente de la siguiente manera (inferencia del modelo completo basado en la teoría de relaciones mencionada):

**Definiciones:**

*   Sea $D_1, D_2, \dots, D_n$ un conjunto de dominios (dominios de valores atómicos).
*   Una **Relación** $R$ es un subconjunto del producto cartesiano de estos dominios:
    $$ R \subseteq D_1 \times D_2 \times \dots \times D_n $$
*   Una **Tupla** $t$ es un elemento de $R$, representado como una lista ordenada de valores: $t = (a_1, a_2, \dots, a_n)$ donde $a_i \in D_i$.
*   Un **Esquema de Relación** se define como $R(A_1, A_2, \dots, A_n)$, donde $A_i$ son los nombres de los atributos correspondientes a los dominios $D_i$.

**Operaciones del Álgebra Relacional (Inferidas para resolver la "Independencia"):**

Para manipular datos sin dependencias de camino, se define un conjunto de operaciones cerradas sobre relaciones:

1.  **Selección ($\sigma$):** Filtra tuplas que satisfacen un predicado $P$.
    $$ \sigma_P(R) = \{ t \mid t \in R \land P(t) \} $$
2.  **Proyección ($\pi$):** Selecciona columnas específicas, eliminando duplicados.
    $$ \pi_{A_1, \dots, A_k}(R) = \{ t[A_1, \dots, A_k] \mid t \in R \} $$
3.  **Unión ($\cup$), Intersección ($\cap$), Diferencia ($-$):** Operaciones estándar de teoría de conjuntos (requieren esquemas compatibles).
4.  **Producto Cartesiano ($\times$):** Combina todas las tuplas de dos relaciones.
    $$ R_1 \times R_2 = \{ (t_1, t_2) \mid t_1 \in R_1 \land t_2 \in R_2 \} $$
5.  **Join ($\bowtie$):** La operación crítica para reemplazar punteros. Une relaciones basándose en valores coincidentes en atributos comunes, eliminando la necesidad de navegación física.
    $$ R_1 \bowtie_{condition} R_2 = \sigma_{condition}(R_1 \times R_2) $$

**Modelo de Optimización (La "Trampa de Conexión"):**

En modelos de red, la eficiencia depende de la ruta $P$. En el modelo relacional, la eficiencia es una responsabilidad del sistema de gestión (SGBD), no del usuario.
*   *Problema de Red:* $Result = Navigate(Root \to P_1 \to P_2 \dots \to Target)$
*   *Solución Relacional:* $Result = \pi_{attrs}(R_1 \bowtie R_2 \bowtie \dots \bowtie R_k)$
La optimización del camino se traslada al interior del motor, preservando la independencia del usuario.

## 3. Análisis Crítico y Derivaciones

**Consistencia Lógica Interna:**

El argumento de Codd es elegante en su simplicidad:
1.  Los sistemas actuales atan la lógica de negocio a la estructura de almacenamiento (punteros/índices).
2.  El almacenamiento físico es mutable y optimizable; la lógica de negocio debe ser estable.
3.  Por tanto, la interfaz de datos debe ser matemáticamente independiente de la implementación física.
4.  La teoría de relaciones provee esta independencia porque los conjuntos y sus operaciones son abstractos por definición.

**Implicaciones de los Resultados:**

*   **Eliminación de la "Trampa de Conexión" (Connection Trap):** En modelos de red, si la estructura de conexiones cambia (ej. un nuevo tipo de relación), los programas que navegan esos caminos deben reescribirse. En el modelo relacional, mientras la semántica de los datos (qué datos existen) no cambie, el usuario no nota cambios en la organización.
*   **Redundancia y Consistencia:** El modelo permite definir formalmente qué datos son redundantes y cómo mantener la consistencia a través de restricciones basadas en la teoría (llaves candidatas, claves foráneas), en lugar de depender de la integridad referencial mantenida por punteros físicos que pueden romperse.

**Limitaciones y Contraejemplos Teóricos (Perspectiva Histórica):**

*   **Costo Computacional Inicial:** En 1970, la abstracción relacional era vista como ineficiente comparada con la navegación directa de punteros. La promesa de Codd era que el SGBD podría optimizar las consultas (transformar álgebra en caminos físicos eficientes) mejor que cualquier programador humano.
*   **Complejidad de la Implementación:** El texto admite que "las implementaciones de sistemas... no se discuten". La teoría era sólida, pero la ingeniería para crear un optimizador de consultas capaz de igualar el rendimiento de la navegación manual fue un desafío monumental que tomó décadas.
*   **Datos No Estructurados:** El modelo asume datos atómicos y tabulares. No abordaba nativamente datos complejos, jerárquicos profundos o no estructurados (aunque esto se resolvió más tarde con XML/JSON o modelos NoSQL, que a menudo reintroducen problemas de independencia).

## 4. Síntesis Rigurosa

El artículo de Codd establece un cambio de paradigma fundamental: el paso de la **gestión de datos basada en navegación** (imperativa, dependiente de la estructura física) a la **gestión de datos basada en declaraciones** (declarativa, dependiente de la lógica matemática).

La intuición económica y lógica subyacente es la **desacoplamiento**. Al formalizar los datos como relaciones $n$-arias y las operaciones como un álgebra cerrada, se elimina la fricción entre la evolución de los requisitos de datos y la estabilidad del software. La formalización matemática no es solo una herramienta de descripción, sino el mecanismo de protección que garantiza que los cambios en la infraestructura de hardware o en los índices de acceso sean transparentes para el usuario final.

La "estructura natural" de los datos es, en última instancia, la estructura lógica que el usuario entiende, no la estructura física que la máquina utiliza. El modelo relacional es la única arquitectura propuesta hasta la fecha que cumple rigurosamente con este axioma de independencia, sentando las bases para la universalidad de los lenguajes de consulta (como SQL, derivado de este trabajo) y la longevidad de los sistemas de gestión de bases de datos modernos.

El argumento central de Codd postula una distinción ontológica irreductible entre el "orden de presentación" (la vista lógica y semántica de los datos para el usuario) y el "orden almacenado" (la implementación física en disco). Los sistemas de la época, como IMS y IDS, fallaban al no distinguir estos niveles, permitiendo que la lógica de las aplicaciones se acoplara a estructuras físicas específicas (punteros, cadenas, árboles). Codd demuestra lógicamente que si un programa depende de una ruta de acceso específica (ej. navegar de "Partes" a "Proyectos" a través de un árbol anidado), cualquier reorganización física o cambio en la estructura de la base de datos (como cambiar a una vista donde "Proyectos" sean los padres) invalida inmediatamente el programa.

La lógica del autor se reconstruye en tres pasos:

Inmutabilidad Falsa: Los sistemas actuales asumen que la estructura física (árboles o redes) es estática y que los programas pueden aprovecharla para el rendimiento.
Fragilidad de la Dependencia: Cualquier cambio en la estructura de almacenamiento (necesario para optimizar nuevas consultas o manejar crecimiento) obliga a reescribir los programas, ya que estos no operan sobre la información en sí, sino sobre la ruta de acceso a ella.
Necesidad de Independencia: Se requiere un modelo donde la estructura lógica sea independiente de la física, permitiendo que los índices y rutas se creen o destruyan sin afectar la validez de las consultas de alto nivel.
El contexto teórico es la transición de los sistemas de archivos y bases de datos jerárquicas hacia el modelo relacional. El objetivo es demostrar la insuficiencia de los modelos de punteros y jerarquías para soportar entornos de datos compartidos y cambiantes, sentando las bases para la independencia de datos que define el modelo relacional.

** Desglose de Conceptos y Formalización Matemática

*** Conceptos Técnicos

Stored Ordering (Orden Almacenado): La secuencia física de registros en el medio de almacenamiento. En los sistemas antiguos, esto determinaba la relación lógica entre datos.
Order of Presentation (Orden de Presentación): La secuencia lógica o semántica en la que los datos son interpretados por la aplicación o el usuario, independiente de su ubicación física.
Indexing Dependence (Dependencia de Indexación): La condición en la que la corrección de un programa depende de la existencia, nombre o estructura específica de un índice físico.
Access Path Dependence (Dependencia de Ruta de Acceso): La situación donde la lógica de navegación de los datos (cómo se llega de A a B) está codificada en el programa basada en una estructura de árbol o red específica.
Hierarchic/Network Model (Modelo Jerárquico/Red): Estructuras de datos donde los registros están conectados explícitamente mediante punteros o cadenas, formando árboles o grafos dirigidos.
*** Formalización Matemática y Lógica

Aunque el texto es descriptivo, la estructura lógica de la dependencia se puede modelar algebraicamente.

Definamos:

$D$: El conjunto de datos (información semántica).
$S$: La estructura física de almacenamiento (árboles, redes, orden de disco).
$P$: El programa de aplicación.
$I$: El conjunto de índices disponibles.
$f_{view}$: La función de vista que mapea datos físicos a lógica.
En un sistema ideal (Relacional), la independencia de datos implica: $$ P(D) \text{ es independiente de } S \text{ y } I $$ $$ \forall s \in S, \forall i \in I: \text{Validez}(P) = \text{constante} $$

En los sistemas criticados por Codd (Jerárquicos/Red), el programa $P$ depende explícitamente de una ruta de acceso específica $R$ dentro de la estructura $S$: $$ P = f(D, R_S) $$ Donde $R_S$ es la ruta de navegación definida por la estructura física $S$.

Si la estructura cambia de $S_1$ a $S_2$ (ej. cambiar de "Partes subordinadas a Proyectos" a "Proyectos subordinados a Partes"), la ruta $R_{S_1}$ deja de existir o cambia de significado: $$ S_1 \xrightarrow{\text{cambio}} S_2 \implies R_{S_1} \neq R_{S_2} $$ $$ \therefore P(D, R_{S_1}) \text{ falla si se ejecuta sobre } S_2 $$

Modelización de las Estructuras (Ejemplo de Partes y Proyectos): Sean $Part$ y $Project$ como conjuntos de entidades. Sea $Commitment$ la relación entre ellas.

En el Modelo Jerárquico (Estructura 1 del texto), la estructura física impone una relación de padre-hijo: $$ Structure_1 = { (p, {pr}) \mid p \in Part, pr \in Project } $$ Aquí, navegar de $Part$ a $Project$ es una operación de "hijo" directa. Si cambiamos a Estructura 2 ($Project$ como padre): $$ Structure_2 = { (pr, {p}) \mid pr \in Project, p \in Part } $$ La función de acceso del programa $Access(Part \to Project)$ definida para $Structure_1$ requiere un puntero descendente. En $Structure_2$, ese puntero no existe en la misma dirección, requiriendo una búsqueda inversa o un cambio de código.

La formalización del problema de independencia se puede expresar como la búsqueda de una función de mapeo $\phi$ tal que: $$ \forall \sigma \in \Sigma \text{ (estructuras físicas)}, \exists \phi_\sigma: \text{Lógica} \to \sigma $$ Donde la interfaz de la aplicación $A$ interactúa solo con Lógica, y $\phi_\sigma$ es manejado internamente por el SGBD, haciendo que $A$ sea invariante bajo cambios en $\sigma$.

** Importancia y Relevancia Teórica

Este texto es la piedra angular teórica que justifica el surgimiento del modelo relacional. Su importancia radica en:

Fundamentación de la Independencia de Datos: Codd establece por primera vez de manera formal y crítica que la separación entre la lógica de los datos y su almacenamiento no es una optimización, sino un requisito de corrección para sistemas de gran escala. Sin esto, el mantenimiento de software en bases de datos sería imposible a medida que los requisitos de negocio cambian.
Crítica a los Punteros y Navegación: El análisis demuestra que el uso de punteros físicos y rutas de navegación (cadenas en IDS, árboles en IMS) introduce una fragilidad inherente. Esto justifica el abandono de la navegación explícita a favor de la declaración de qué datos se necesitan (lógica relacional/SQL) en lugar de cómo acceder a ellos.
Implicaciones Metodológicas: El texto obliga a un cambio de paradigma: de diseñar la base de datos pensando en la eficiencia de acceso inmediato (optimización prematura de rutas) a diseñar la estructura lógica normalizada y permitir que el sistema gestione las rutas de acceso (índices) dinámicamente.
Solución a Problemas Previos: Resuelve el problema de la "parálisis del esquema", donde las empresas no podían modificar sus estructuras de datos por miedo a romper aplicaciones críticas. El modelo relacional permite añadir índices o reorganizar datos físicamente sin tocar una línea de código de la aplicación.
Limitaciones y Supuestos:
El texto asume que el costo computacional de traducir consultas lógicas a rutas físicas eficientes es aceptable (lo cual fue cierto con el tiempo y mejoró con optimizadores), mientras que en 1970 los sistemas jerárquicos eran más rápidos para transacciones simples específicas.

El texto de la página 380 de Codd constituye el núcleo de la transición del modelo relacional matemático (basado en conjuntos ordenados) al modelo relacional lógico (basado en conjuntos desordenados por nombres). El argumento central es que la dependencia de la posición de los dominios en una relación (ordenamiento implícito) introduce una fragilidad semántica y operativa inaceptable para el usuario final, especialmente en esquemas de alta aridez (grado elevado, como 30).

Codd postula una distinción fundamental entre:

Relación (Mathematical Relation): Un conjunto ordenado de tuplas donde la posición de los atributos es significativa ($A_1, A_2, \dots, A_n$). Cambiar el orden cambia la relación.
Relación Lógica (User Relationship): Una entidad desordenada donde la identidad de los dominios se define por su nombre de rol (role name), no por su posición.
La lógica del argumento se construye así:

Premisa 1: En sistemas complejos, el orden de los dominios es arbitrario y difícil de recordar para el usuario.
Premisa 2: Si el usuario debe depender de la posición (ej. "el tercer campo es el proyecto"), cualquier reordenamiento físico o lógico rompe la semántica de la consulta.
Conclusión: El usuario debe interactuar con relaciones desordenadas, donde cada dominio está calificado por un nombre de rol único (ej. sub.part, super.part). Esto permite que la estructura de datos sea invariante ante permutaciones de posición.
El texto introduce también la formalización de conceptos de integridad y referencia:

Dominio Activo: El subconjunto de valores que realmente existen en la base de datos en un instante dado ($ActiveDomain \subseteq Domain$).
Clave Primaria (Primary Key): Un dominio (o combinación) que identifica únicamente cada tupla. Debe ser no redundante (ningún subconjunto de sus componentes es superfluo).
Clave Foránea (Foreign Key): Un dominio que referencia la clave primaria de otra relación (o de sí misma), estableciendo la integridad referencial sin necesidad de punteros físicos.
Dominios No Simples: Permiten que los elementos de un dominio sean ellos mismos relaciones (relaciones anidadas), lo que anticipa la recursividad y la capacidad de manejar datos complejos dentro del marco relacional.
El objetivo es desvincular la lógica de la implementación, estableciendo que la "identidad" de un atributo es su nombre, no su índice. Esto resuelve el problema de la rigidez de los sistemas jerárquicos y de red, donde la estructura de acceso era fija.

** Desglose de Conceptos y Formalización Matemática

*** Conceptos Técnicos

Dominio Ordenado vs. Desordenado:
Ordenado: La identidad del atributo depende de su índice $i$ en la tupla.
Desordenado: La identidad depende de un nombre de rol $n_i$.
Role Name (Nombre de Rol): Un identificador semántico que califica un dominio para distinguir su función dentro de la relación (ej. supplier_id vs. part_id en una relación de suministro).
Active Domain (Dominio Activo): El conjunto de valores reales presentes en la base de datos en un momento $t$. $$ ActiveDomain(R, A, t) \subseteq Domain(A) $$
Primary Key (Clave Primaria): Subconjunto de dominios $K \subseteq {D_1, \dots, D_n}$ tal que para cualquier par de tuplas $t_1, t_2 \in R$, si $t_1[K] = t_2[K]$ entonces $t_1 = t_2$. Debe ser mínimo (no redundante).
Foreign Key (Clave Foránea): Dominio $F$ en relación $R$ cuyos valores deben coincidir con los valores de una clave primaria $P$ en relación $S$ (o $R$ misma).
Nonsimple Domain (Dominio No Simple): Un dominio cuyos elementos son conjuntos de valores o relaciones enteras (ej. un historial de salarios es una relación de fechas y montos).
Repeating Group: (Mención de terminología obsoleta) Grupos de valores repetidos que el modelo relacional busca eliminar en favor de relaciones planas.
*** Formalización Matemática y Lógica

A. Relaciones Desordenadas (User Relationships)

Sea $R$ una relación de grado $n$. En el modelo matemático tradicional, es un subconjunto de un producto cartesiano ordenado: $$ R \subseteq D_1 \times D_2 \times \dots \times D_n $$ Una tupla $t$ es una secuencia $(v_1, v_2, \dots, v_n)$ donde $v_i \in D_i$.

En el modelo propuesto por Codd, la relación es un conjunto de asociaciones nombre-valor. Definimos una relación como un conjunto de funciones parciales o diccionarios: $$ R = { f \mid f: {N_1, \dots, N_k} \to \bigcup_{i=1}^n D_i, \text{ donde } f(N_i) \in D_i } $$ Donde $N_i$ son los nombres de rol (role names) que identifican los dominios, no sus posiciones. Si hay dominios idénticos (mismo tipo de dato), se requiere calificación: $$ \text{dom}(N_i) = D, \quad \text{dom}(N_j) = D, \quad i \neq j \implies N_i \neq N_j \text{ (por rol)} $$ Ejemplo del texto: component tiene dominios sub.part, super.part, quantity. La tupla $t$ se representa como: $$ t = { (\text{sub.part}, p_1), (\text{super.part}, p_2), (\text{quantity}, q) } $$ El orden de estos pares es irrelevante.

B. Integridad de Claves

Clave Primaria (Primary Key): Sea $K = {A_1, \dots, A_m}$ un subconjunto de atributos de $R$. $$ \forall t_1, t_2 \in R: \left( \forall A_i \in K, t_1[A_i] = t_2[A_i] \right) \implies t_1 = t_2 $$ No Redundancia: $K$ es mínima si para todo $A_j \in K$, el conjunto $K \setminus {A_j}$ no satisface la condición de unicidad.

Clave Foránea (Foreign Key): Sea $F$ un conjunto de atributos en $R$ y $P$ una clave primaria en $S$. $$ \forall t \in R: t[F] \in \pi_F(\sigma_{P=t[P]}(S)) $$ O más simplemente: $$ \pi_F(R) \subseteq \pi_P(S) $$ Esto asegura que cada valor en la clave foránea existe como clave primaria en la relación referenciada.

C. Dominios No Simples y Recursividad

Si un dominio $D_{hist}$ es "no simple", su conjunto de valores son relaciones. Sea $D_{salary_hist} = { r \mid r \subseteq \text{Date} \times \text{Amount} }$. Una tupla en la relación employee puede tener un valor $h \in D_{salary_hist}$: $$ t_{emp} = { (\text{name}, \text{"John"}), (\text{salary_hist}, h) } $$ Donde $h = { (\text{date}_1, \text{amount}_1), (\text{date}_2, \text{amount}_2), \dots }$. Esto formaliza la capacidad de almacenar estructuras de datos complejas dentro de un dominio atómico en el nivel superior, manteniendo la integridad relacional.

D. Dominio Activo

El dominio activo es dinámico: $$ ActiveDomain(R, A, t) = { v \mid \exists t' \in R(t'), t'[A] = v } $$ Contraste con el dominio teórico (todos los valores posibles): $$ ActiveDomain(R, A, t) \subseteq Domain(A) $$

** Importancia y Relevancia Teórica

Este fragmento es crucial porque formaliza la abstracción de datos que permite que el modelo relacional sea usable en la práctica, no solo teóricamente.

Innovación en la Interacción Humano-Máquina: Al proponer la independencia del orden de los dominios, Codd elimina la carga cognitiva de recordar la posición de los atributos. Esto es fundamental para la usabilidad de SQL y los lenguajes declarativos. El usuario dice "elige el nombre", no "elige el tercer campo".

Integridad Referencial sin Punteros: La definición de claves foráneas como valores (no punteros) permite que la integridad de los datos sea una propiedad lógica del conjunto de datos, no una propiedad de la estructura física de acceso. Esto facilita la normalización, la integridad y la portabilidad de los datos.

Generalización del Modelo: La inclusión de dominios no simples y la capacidad de manejar relaciones anidadas amplían el alcance del modelo relacional más allá de tablas planas, anticipando conceptos modernos de bases de datos semirrelacionales y JSON.

Crítica a la Terminología Obsoleta: Al vincular los conceptos de "atributo" y "repeating group" (términos de sistemas jerárquicos) con dominios simples y no simples, Codd proporciona un marco teórico para migrar y reemplazar sistemas antiguos sin perder la semántica.

Diseño de Esquemas: Obliga a los diseñadores a pensar en nombres semánticos y roles, no en archivos físicos.
Optimización: El sistema debe traducir consultas basadas en nombres a rutas de acceso físicas eficientes, un desafío que impulsó el desarrollo de optimizadores de consultas.

Limitaciones y Supuestos:

Asume que el sistema de gestión puede manejar eficientemente la sobrecarga de verificar integridad referencial en claves foráneas en tiempo real (un problema de rendimiento que se resolvió con índices y restricciones diferidas).
Asume que los usuarios pueden abstraerse completamente de la estructura física, lo cual a veces requiere compromisos en sistemas de alto rendimiento específico.
La formalización de dominios no simples introduce complejidad en la consulta y el procesamiento, lo que eventualmente llevó a la distinción entre modelos relacionales puros y modelos orientados a objetos.

El texto de la página 381 introduce el concepto fundamental de Forma Normal (Normal Form) y el procedimiento de normalización como mecanismo para eliminar dominios no simples (nonsimple domains) y garantizar que toda relación pueda representarse como un arreglo bidimensional homogéneo. Codd argumenta que la complejidad y la confusión en los sistemas de bases de datos de la época surgían de la mezcla entre tipos de datos e instancias, y entre el modelo lógico y la representación física (ej. el uso ambiguo del término "registro").

La lógica del autor se desarrolla en tres etapas:

Identificación del Problema: Los dominios no simples (como un historial de salarios dentro de un registro de empleado) requieren estructuras de datos complejas (punteros, listas anidados) que rompen la simplicidad del modelo relacional y dificultan el almacenamiento y la comunicación de datos.
Propuesta de Solución (Normalización): Se define un algoritmo sistemático para "desanidar" estas estructuras. El proceso implica tomar la clave primaria de una relación padre e insertarla en cada relación hija subordinada, convirtiendo así los dominios anidados en relaciones independientes y planas.
Condiciones de Validez: El algoritmo requiere que las relaciones no normalizadas formen un árbol de dependencias y que ninguna clave primaria contenga dominios no simples. Si se cumplen, el resultado es un conjunto de relaciones en forma normal donde cada relación es un conjunto de tuplas atómicas.
El objetivo teórico es demostrar que cualquier estructura de datos jerárquica o anidada puede ser transformada en un conjunto de relaciones planas sin pérdida de información, eliminando la necesidad de punteros y listas de ordenación. Esto sienta las bases para la independencia de datos física y lógica, permitiendo que la representación de datos sea un simple arreglo bidimensional, ideal para la comunicación entre sistemas heterogéneos y para el almacenamiento eficiente.

Además, el texto anticipa la base lingüística del modelo: al estar en forma normal, el lenguaje de consulta puede basarse en un cálculo de predicados de primer orden, lo que proporciona un marco formal riguroso para la expresión de consultas y restricciones.

** Desglose de Conceptos y Formalización Matemática

*** Conceptos Técnicos

Dominio Simple (Simple Domain): Un dominio cuyos elementos son valores atómicos (no descomponibles) y no contienen estructuras internas.
Dominio No Simple (Nonsimple Domain): Un dominio cuyos elementos son a su vez relaciones o estructuras de datos complejas (ej. un historial de salarios, una lista de hijos).
Forma Normal (Normal Form): Una relación donde todos los dominios son simples. No hay atributos anidados ni grupos repetidos.
Normalización: El proceso algorítmico de transformar una colección de relaciones con dominios no simples en un conjunto de relaciones en forma normal.
Árbol de Dependencias: La estructura jerárquica que describe cómo los dominios no simples se relacionan entre sí (padre-hijo).
Cálculo de Predicados de Primer Orden: El sistema lógico formal que basta para expresar todas las consultas necesarias sobre relaciones en forma normal.
Sublenguaje de Datos (Data Sublanguage): Un lenguaje dedicado (denotado como $R$) basado en lógica de predicados, separado del lenguaje de host ($H$), para manipular relaciones.
*** Formalización Matemática y Lógica

A. Definición de Normalización

Sea $R$ una relación con un dominio no simple $D_{ns}$. $$ R = { (k, d_1, \dots, d_n, D_{ns}) } $$ Donde $k$ es la clave primaria y $D_{ns}$ es una relación anidada $R'$. El proceso de normalización transforma esto en dos relaciones:

$R_{padre} = { (k, d_1, \dots, d_n) }$
$R_{hijo} = { (k, k', d'_1, \dots, d'_m) }$ Donde $k'$ es la clave primaria de $R'$, y $k$ se ha insertado en $R'$ como clave foránea, formando una nueva clave compuesta $(k, k')$.
B. Algoritmo de Expansión de Claves

Sea $P$ la relación padre con clave $K_P$. Sea $C$ la relación hija con clave $K_C$. La relación hija normalizada $C'$ tendrá: $$ K_{C'} = K_P \cup K_C $$ $$ C' = { (k_p, k_c, \text{atributos de } C) \mid \exists t \in C, t[K_C] = k_c \land t[\text{padre}] = k_p } $$ Este proceso se repite recursivamente para cada nivel del árbol de dependencias.

C. Condiciones de Validez

Estructura de Árbol: Sea $G = (V, E)$ el grafo de dependencias de dominios no simples. $$ G \text{ es un bosque (colección de árboles)} \iff \forall v \in V, \text{grado de entrada}(v) \le 1 \land \text{no hay ciclos} $$
Claves Simples: $$ \forall K \in \text{Keys}(R), \forall d \in K: \text{es_simple}(d) = \text{true} $$
D. Representación en Forma Normal

Una relación en forma normal $R$ se representa como un arreglo bidimensional: $$ R[i] [j] \in \text{Dom}(A_j) $$ Donde $A_j$ son los atributos (dominios simples). La sintaxis de acceso a datos se simplifica a: $$ \text{Nombre} = R(g).r.d $$ Donde:

$R$: Nombre de la relación.
$g$: Identificador de generación (opcional).
$r$: Nombre de rol (opcional, si hay ambigüedad de dominios).
$d$: Nombre del dominio. Si no hay ambigüedad ni múltiples generaciones: $R.d$.
E. Lenguaje de Datos basado en Lógica de Primer Orden

El sublenguaje $R$ permite expresiones como: $$ { t \mid R(t) \land P(t) } $$ Donde $P(t)$ es una fórmula en cálculo de predicados de primer orden sobre los atributos de $t$. La capacidad expresiva de $R$ es equivalente a la del álgebra relacional cuando las relaciones están en forma normal.

** Importancia y Relevancia Teórica

Este texto es seminal porque establece los cimientos de la teoría de normalización y la arquitectura de lenguajes de bases de datos.

Fundamento de la Normalización: Codd introduce formalmente el concepto de eliminar dominios no simples para lograr la 1ª Forma Normal (1NF). Esto es crucial para evitar anomalías de inserción, actualización y borrado que surgen de los grupos repetidos y la anidación.

Simplicidad de Representación: Al demostrar que cualquier estructura compleja puede aplanarse, Codd justifica el uso de arreglos bidimensionales como estructura de almacenamiento universal. Esto simplifica drásticamente la implementación de SGBD y facilita el intercambio de datos (interoperabilidad).

Base Lógica Formal: La afirmación de que "el cálculo de predicados de primer orden basta" si las relaciones están en forma normal es un hito. Conecta la teoría de conjuntos y lógica con la práctica de las bases de datos, permitiendo que las consultas sean expresadas de manera declarativa y formalmente verificables. Esto es el germen de SQL.

Separación de Responsabilidades: La distinción entre el sublenguaje de datos ($R$) y el lenguaje de host ($H$) anticipa la arquitectura moderna de capas en las aplicaciones de bases de datos, donde la lógica de datos se separa de la lógica de negocio y la presentación.

Implicaciones Prácticas:

Diseño de Esquemas: Proporciona un método sistemático para diseñar bases de datos libres de redundancia y anomalías.
Optimización: Las relaciones en forma normal son más fáciles de indexar y optimizar, ya que no requieren manejo de punteros anidados o listas complejas.
Interoperabilidad: El formato de comunicación basado en arreglos comprimidos sin punteros permite el intercambio de datos entre sistemas heterogéneos, un precursor de formatos como CSV o JSON en contextos de intercambio.
Limitaciones y Supuestos:

Asume que la normalización total siempre es deseable. En la práctica, la desnormalización ocasional es necesaria para optimizar el rendimiento de consultas complejas (un trade-off que Codd reconoce implícitamente al mencionar que "no se discuten otras operaciones de normalización").
El enfoque en lógica de primer orden puede ser limitante para ciertos tipos de consultas recursivas o complejas que requieren lógica de orden superior (aunque esto se resolvió posteriormente con extensiones de SQL).
La suposición de que todos los dominios pueden hacerse simples puede ser restrictiva para datos semiestructurados o complejos (como documentos XML o JSON modernos), aunque el modelo relacional ha evolucionado para manejar estos casos mediante tipos de datos especializados.
Este trabajo cierra la trilogía de la teoría relacional: independencia de estructura (p. 378), independencia de representación (p. 380) y normalización/forma normal (p. 381), proporcionando un marco completo y riguroso para el diseño y gestión de bases de datos relacionales.

Las funciones aritméticas y de lógica se delegan al lenguaje de host ($H$), manteniendo $R$ limpio y declarativo.

Esto significa que cualquier combinación de atributos puede servir como "entrada" (conocida) para recuperar los "restantes" (desconocidos), sin importar el orden de almacenamiento. Codd demuestra que lograr esto en sistemas navegacionales requeriría $n!$ caminos nombrados, mientras que el modelo relacional lo hace con una sola relación nombrada.
Clasificación de Relaciones: Se introducen distinciones formales entre:
Conjunto Nombrado (Named Set): Relaciones explícitamente declaradas por los usuarios (almacenadas o vistas derivadas con nombre).
Conjunto Expresible (Expressible Set): El conjunto universal de todas las relaciones que pueden derivarse mediante expresiones lógicas sobre el conjunto nombrado.
Conjunto Almacenado (Stored Set): Las representaciones físicas subyacentes.
El objetivo es demostrar que el modelo relacional reduce drásticamente la complejidad cognitiva y de gestión para el usuario. En lugar de definir múltiples estructuras de acceso (caminos) para cada tipo de consulta, el usuario define una sola relación lógica y deja que el sistema traduzca cualquier consulta simétrica en operaciones eficientes sobre el almacenamiento físico. Esto resuelve el problema de la "fragilidad" de los programas en sistemas antiguos, donde cambiar la ruta de acceso exigía reescribir el código.

This is a system feature ... which we shall call (logically) symmetric exploitation of relations. #+END_QUOTE Justificación: Introduce el concepto de explotación simétrica, una propiedad fundamental del modelo relacional que lo distingue de los sistemas navegacionales. Es la base de la flexibilidad de las consultas SQL.

#+BEGIN_QUOTE To support symmetric exploitation of a single binary relation, two directed paths are needed. For a relation of degree n, the number of paths to be named and controlled is n factorial. #+END_QUOTE Justificación: Proporciona una prueba combinatoria de la ineficiencia de los modelos navegacionales frente al relacional. Muestra cómo el costo de soportar consultas inversas crece factorialmente en sistemas de punteros.

#+BEGIN_QUOTE The named set is the collection of all those relations that the community of users can identify b y means of a simple name... The expressible set is the total collection of relations that can be designated b y expressions in the data language. #+END_QUOTE Justificación: Establece la jerarquía formal de relaciones: el conjunto nombrado (explícito) es un subconjunto del conjunto expresible (derivado lógicamente), lo que permite la creación de vistas y consultas complejas sin almacenamiento físico adicional.

#+BEGIN_QUOTE Ideally, the variety of permitted data representations should be just adequate to cover the spectrum of performance requirements... responsibility for providing efficient response and throughput shifts from the individual user to the data system. #+END_QUOTE Justificación: Enuncia el principio de independencia de datos física y el cambio de responsabilidad: el usuario se preocupa por la lógica, el sistema (optimizador) por la eficiencia física.

** Desglose de Conceptos y Formalización Matemática

*** Conceptos Técnicos

Lenguaje de Subdatos ($R$): El lenguaje dedicado a la manipulación de datos, basado en lógica de predicados.
Lenguaje de Host ($H$): El lenguaje de programación general (ej. COBOL, PL/I) donde se definen funciones aritméticas y de lógica de negocio.
Explotación Simétrica (Symmetric Exploitation): La capacidad de utilizar cualquier subconjunto de atributos de una relación como filtro (entrada) para recuperar los demás, sin restricción de dirección.
Conjunto Nombrado (Named Set): $\mathcal{N} = { R_1, R_2, \dots, R_k }$, relaciones declaradas explícitamente.
Conjunto Expresible (Expressible Set): $\mathcal{E}$, el conjunto cerrado bajo operaciones lógicas y relacionales sobre $\mathcal{N}$. $\mathcal{N} \subset \mathcal{E}$.
Conjunto Almacenado (Stored Set): $\mathcal{S}$, las representaciones físicas de las relaciones.
Forma Prenex: Una forma normal lógica donde todos los cuantificadores se mueven al principio de la fórmula, suficiente para expresar cualquier consulta sin perder poder descriptivo.
Dependencias de Actualización/Borrado: Reglas declarativas que especifican que la modificación de una relación debe propagar cambios a otras (análogo a triggers o integridad referencial en cascada).
*** Formalización Matemática y Lógica

A. Poder Descriptivo y Lógica de Predicados

Una consulta en $R$ especifica un subconjunto $Q$ de una relación $R$: $$ Q = { t \in R \mid \phi(t) } $$ Donde $\phi(t)$ es una fórmula bien formada (wff) del cálculo de predicados de primer orden. El lenguaje es universal si: $$ \forall \psi \in \text{WFF}(\text{PredCalc}), \exists \phi \in \text{Syntax}(R) \text{ tal que } \phi \equiv \psi $$ Codd nota que no se necesita toda la sintaxis, basta con la forma prenex: $$ \phi = Q_1 x_1 Q_2 x_2 \dots Q_n x_n (M) $$ Donde $Q_i \in {\forall, \exists}$ y $M$ es una fórmula libre de cuantificadores (matriz).

B. Simetría y Complejidad de Caminos

Sea $R$ una relación de grado $n$ con atributos ${A_1, A_2, \dots, A_n}$. Para una consulta que fija un subconjunto $K \subset {A_i}$ de tamaño $k$ y busca el complemento $U = {A_i} \setminus K$:

Modelo Relacional: Requiere 1 nombre de relación. La consulta es: $$ \pi_U (\sigma_{K = v} (R)) $$
Modelo Navegacional (Punteros): Requiere definir un camino dirigido para cada posible dirección de búsqueda. El número de direcciones necesarias es el número de permutaciones de los atributos: $$ N_{paths} = n! $$ Ejemplo para $n=4$ (relación supply): $4! = 24$ caminos potenciales, o al menos uno para cada partición de entradas/salidas. Si se usan solo relaciones binarias anidadas, el número de nombres necesarios es $2n - 1$. Para $n=4$: $2(4) - 1 = 7$ nombres, en lugar de $n+1 = 5$ en notación $n$-aria directa.
C. Conjuntos de Relaciones

Conjunto Nombrado: $$ \mathcal{N} = { R \mid \text{DECLARED}(R) } $$
Conjunto Expresible: $$ \mathcal{E} = \text{Closure}(\mathcal{N}, \text{Operaciones Relacionales}, \text{Lógica}) $$ Las operaciones incluyen: unión, diferencia, producto cartesiano, selección, proyección, y cuantificación.
Relación entre Conjuntos: $$ \mathcal{N} \subseteq \mathcal{E} $$ $$ \mathcal{S} \xrightarrow{\text{mapeo}} \mathcal{N} $$ El sistema debe traducir cualquier $E \in \mathcal{E}$ a operaciones sobre $\mathcal{S}$ de manera eficiente.
D. Dependencias de Actualización

Si se declara una dependencia de borrado en cascada entre $R_1$ y $R_2$: $$ \forall t_1 \in R_1, t_2 \in R_2: (t_1[K] = t_2[F] \land \text{DELETE}(t_1)) \implies \text{DELETE}(t_2) $$ Esto se declara en $R$ y se ejecuta automáticamente, moviendo la lógica de integridad del código de la aplicación al sistema.

** Importancia y Relevancia Teórica

Este texto es fundamental porque establece la arquitectura de la independencia de datos y la filosofía de diseño de los SGBD modernos.

Fundamento de la Simetría Relacional: La idea de "explotación simétrica" es la razón principal por la que el modelo relacional es tan potente. Permite consultas ad-hoc que no estaban previstas al diseñar la base de datos. En sistemas navegacionales, si no se definió el camino inverso, la consulta es imposible sin reescribir el software. Esto democratiza el acceso a los datos.

Separación de Lógica y Física: Al afirmar que la responsabilidad de la eficiencia se traslada del usuario al sistema, Codd anticipa el desarrollo de optimizadores de consultas. El usuario solo describe qué quiere, el sistema decide cómo obtenerlo (índices, joins, ordenamiento). Esto es el corazón de SQL y de todos los SGBD comerciales.

Jerarquía de Relaciones: La distinción entre conjunto nombrado, expresible y almacenado es crucial para entender las vistas (views) y la abstracción. Permite crear capas lógicas sobre datos físicos sin duplicación, facilitando la seguridad y la personalización de la información para diferentes usuarios.

Lenguaje Declarativo: Al limitar el poder de cómputo del lenguaje de datos y centrarse en la descripción lógica, Codd allana el camino para lenguajes declarativos como SQL. Esto reduce la complejidad del código de la aplicación y minimiza errores.

Eficiencia en el Diseño: La demostración de que los modelos navegacionales requieren un número factorial de caminos para lograr la misma flexibilidad que una relación relacional es un argumento matemático contundente a favor del modelo relacional. Explica por qué los sistemas de red y jerárquicos eran tan rígidos y difíciles de mantener.

Implicaciones Prácticas:

Seguridad: El sistema puede aplicar restricciones de seguridad a nivel de relación o atributo sin modificar el código de la aplicación.
Mantenibilidad: Cambios en la estructura física (índices, particionamiento) no afectan las aplicaciones.
Interoperabilidad: La estandarización del lenguaje de datos (basado en lógica) facilita la integración de sistemas.
Limitaciones y Supuestos:

Asume que el optimizador del sistema será lo suficientemente inteligente para traducir consultas simétricas en rutas físicas eficientes. En las primeras implementaciones, esto fue un desafío significativo.
La suposición de que las funciones de lógica de negocio deben estar en el lenguaje de host ($H$) y no en el de datos ($R$) ha evolucionado con los procedimientos almacenados y triggers, que traen lógica compleja de vuelta al servidor de bases de datos.
El enfoque en lógica de primer orden puede ser insuficiente para ciertos tipos de análisis recursivo complejo (aunque se han añadido extensiones como WITH RECURSIVE en SQL moderno).
